## 四、Bug 列表与修复记录

### 4.1 已修复 Bug

**BUG-001：销售漏斗完全不显示（严重程度：高）**

- **发现时间**：开发 Day 12（仪表盘集成阶段）
- **现象**：访问仪表盘和独立漏斗页面，ECharts 漏斗图区域为空白，无任何渲染内容
- **原因分析**：`funnel-chart.js` 使用 ECharts 5 自定义系列，在 `renderItem` 回调函数中访问了 `params.data.totalStages` 和 `params.data.displayText`。ECharts 5 的 `renderItem` 参数中不包含 `data` 属性，导致 `TypeError: Cannot read properties of undefined`，ECharts 内部静默捕获该异常后不渲染任何图形元素
- **排查过程**：
  1. 首先确认后端数据链路正常 —— `?format=json` 返回正确的 JSON 数组
  2. 创建独立 HTML 测试页面，硬编码数据 + ECharts 内置漏斗渲染成功，排除 CDN 和浏览器问题
  3. 对比测试页面和项目页面的差异，定位到自定义系列 `renderItem` 实现
  4. 查阅 ECharts 5 官方文档，确认 `params` 对象不包含 `data` 属性
- **修复方案**：放弃不稳定的自定义系列，改用 ECharts 内置 `type: "funnel"` 系列；添加 bootcdn 备用 CDN；将 `${funnelJson}` 直接从 EL 嵌入 JS 代码避免 JSON.parse 额外开销
- **影响范围**：`funnel-chart.js`、`funnel_chart.jsp`、`dashboard.jsp`
- **状态**：✅ 已修复

---

**BUG-002：customer_list.jsp 搜索框与其他页面布局不一致（严重程度：低）**

- **发现时间**：开发 Day 11（页面联调阶段）
- **现象**：客户管理页搜索框使用 Bootstrap `input-group` 包裹呈联合输入框样式，而产品、联系人等 5 个列表页使用扁平 `form-inline` 布局
- **原因分析**：客户页面最早开发时参考了不同的 AdminLTE 示例，后续页面使用了统一的扁平模式但未回溯修改客户页面
- **修复方案**：移除 `<div class="input-group">` 和 `<div class="input-group-append">`，改为与其他页面一致的 `<form class="form-inline">` + `mr-2` 间距
- **影响范围**：`customer_list.jsp`
- **状态**：✅ 已修复

---

**BUG-003：FollowUpDao.updateStatus() 缺少 update_time 更新（严重程度：中）**

- **发现时间**：代码审查阶段
- **现象**：逻辑删除跟进记录时，`update_time` 字段不刷新，与其他 6 个 DAO 的同名方法行为不一致
- **原因分析**：FollowUpDao 的 `updateStatus()` 方法 SQL 编写时遗漏了 `,update_time=NOW()`
- **修复方案**：SQL 从 `UPDATE crm_follow_up_record SET status=? WHERE id=?` 改为 `UPDATE crm_follow_up_record SET status=?,update_time=NOW() WHERE id=?`
- **影响范围**：`FollowUpDao.java` 第 206 行
- **状态**：✅ 已修复

---

**BUG-004：ContractDao/OpportunityDao 查询时表别名不匹配导致 SQL 异常（严重程度：高）**

- **发现时间**：开发 Day 10（合同/商机联调阶段）
- **现象**：访问合同列表时报 `Unknown column 'c.owner_user_id' in 'where clause'`
- **原因分析**：ContractDao 的 `scope(sales)` 方法返回 `AND c.owner_user_id=?`，但合同列表 SQL 中客户表别名在某些查询路径下不是 `c`。DAO 重构时统一了 `scope` 方法但未检查所有调用点的 JOIN 别名一致性
- **修复方案**：统一所有 DAO 中客户表别名为 `c`，商机表别名为 `o`，并逐条验证每个 `scope()` 方法的调用上下文
- **影响范围**：`ContractDao.java`、`OpportunityDao.java`
- **状态**：✅ 已修复

---

**BUG-005：Gson 序列化 BigDecimal 产生科学计数法导致漏斗图数值异常（严重程度：中）**

- **发现时间**：开发 Day 14（ECharts 集成阶段）
- **现象**：`?format=json` 接口返回的 `amount` 字段偶尔出现科学计数法，如 `7.44E+4` 而非 `74400.00`，导致前端漏斗图 label 显示异常
- **原因分析**：Gson 默认使用 `Double` 精度序列化 `BigDecimal`，当金额值恰好处于某些范围时会触发科学计数法转换。Gson 2.10.1 的 `ToNumberPolicy` 在特定值下表现不稳定
- **修复方案**：在 FunnelServlet 序列化前，遍历 `List<FunnelData>` 将每个 `amount` 字段通过 `setScale(2, RoundingMode.HALF_UP)` 规范化；同时设置 Gson 实例禁用 HTML 转义和特殊数字策略
- **影响范围**：`FunnelServlet.java`、`DashboardServlet.java`
- **状态**：✅ 已修复

**BUG-006：LoginService.register() 始终返回 true 即使 INSERT 失败（严重程度：中）**

- **发现时间**：代码审查阶段
- **现象**：注册新用户时，`dao.save()` 返回值未检查，方法始终 `return true`。如果 INSERT 因为数据库连接中断等原因静默失败（executeUpdate 返回 0），调用方会认为注册成功
- **原因分析**：开发早期 `register()` 为快速验证通路而写，后续 `ContactService`、`ProductService` 等均改为 `return n > 0` 模式，但 `LoginService` 遗漏
- **修复方案**：改为 `int n = dao.save(conn, user); return n > 0;`
- **影响范围**：`LoginService.java`、同时修复了 `CustomerService.add()` 和 `FollowUpService.add()` 的相同问题
- **状态**：✅ 已修复

---

**BUG-007：CustomerService.transfer() 在事务内用独立连接读取导致连接持有时间过长（严重程度：中）**

- **发现时间**：代码审查阶段
- **现象**：`transfer()` 方法先获取事务连接 `conn` 并 `setAutoCommit(false)`，然后在事务连接闲置状态下用独立 JdbcTemplate 连接执行 `findById()` 读操作。如果读操作阻塞（如数据库锁等待），事务连接被无意义持有
- **原因分析**：开发时为方便，将读操作放在 try 块内靠近写操作的位置，未意识到读写混合时的事务连接管理问题
- **修复方案**：将 `dao.findById(id, null, false)` 移到 `conn = DbHelper.getDataSource().getConnection()` 之前，读操作完成后再获取事务连接执行写操作
- **影响范围**：`CustomerService.java`
- **状态**：✅ 已修复

**BUG-008：ContactDao 和 ProductDao 关键词搜索未 trim 导致搜索行为不一致（严重程度：低）**

- **发现时间**：代码审查阶段
- **现象**：用户在搜索框输入首尾带空格的字符串（如" 星海 "），联系人管理和产品管理的搜索结果异常（LIKE 匹配时空格也被当作搜索内容），而客户管理因为写了 `.trim()` 能正常搜索
- **原因分析**：`CustomerDao` 的关键词处理为 `keyword.trim()`，`ContactDao` 和 `ProductDao` 直接使用原始 `keyword` 未 trim
- **修复方案**：在 `ContactDao` 和 `ProductDao` 的关键词处理中添加 `.trim()`
- **影响范围**：`ContactDao.java`、`ProductDao.java`
- **状态**：✅ 已修复

---

**BUG-009：日期输入框 placeholder 显示浏览器默认"年/月/日"与实际格式不符（严重程度：低）**

- **发现时间**：开发 Day 15（UI 审查阶段）
- **现象**：合同表单和商机表单的 `<input type="date">` 输入框在空白状态下显示浏览器默认的 placeholder 格式（如 Chrome 显示 `yyyy/mm/dd`），与项目中文界面风格不一致
- **原因分析**：HTML `<input type="date">` 的 placeholder 由浏览器控制，无法直接自定义。尝试使用 `type="text"` + `onfocus` 切换为 `type="date"` 的方案会导致回显已保存数据时格式不兼容
- **修复方案**：保持 `type="date"` 使用浏览器原生日期选择器（自带右侧日历图标），不显示自定义提示文字
- **影响范围**：`contract_form.jsp`、`opportunity_form.jsp`、`follow_form.jsp`
- **状态**：✅ 已修复

**BUG-010：验证码字符旋转角度过大导致部分字符几乎不可辨认（严重程度：低）**

- **发现时间**：开发 Day 16（用户体验测试阶段）
- **现象**：验证码增强扭曲效果后，`CheckCodeUtil` 将每个字符的旋转角度设置为 ±38°，错切系数提高到 0.55，导致某些字符（如 'g'、'p'）在极端角度下超出画布边界或被裁剪，人工识别率下降至约 60%
- **原因分析**：增强扭曲时采用了统一的大旋转范围，未考虑不同字符的笔画差异和边界情况。`'g'`、'j'、'p'、'q' 等有下延笔画的字符在大旋转角度下更容易超出可视区域
- **修复方案**：保持 ±38° 旋转范围不变，但将错切系数从 0.55 降低至 0.45，缩放上限从 1.25 降至 1.15；同时尝试了不同字体组合，最终确定 Arial/Serif/SansSerif/Dialog/Monospaced 五种字体混用的方案，平衡了可辨性与防识别效果
- **影响范围**：`CheckCodeUtil.java`
- **状态**：✅ 已修复
